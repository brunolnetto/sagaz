# sagaz on Google Cloud (Terraform)

Deploys the sagaz **outbox worker** (`python -m sagaz.core.outbox.worker`) to
**Cloud Run worker pools**, with **Cloud SQL for PostgreSQL** as the outbox store
and **Memorystore for Redis** as the broker. Used by `sagaz deploy --provider gcp`;
it can also be applied directly.

```
                 VPC (created, or var.network/var.subnetwork)
 ┌──────────────────────────────────────────────────────────────────┐
 │  subnet ── Direct VPC egress ── Cloud Run worker pool (N always-on) │
 │                                     │ DATABASE_URL, REDIS_URL       │
 │                                     │ (Secret Manager env secrets)  │
 │  Private Service Access ───┬── Cloud SQL PostgreSQL 16 (private IP) │
 │                            └── Memorystore Redis (AUTH, private IP) │
 └──────────────────────────────────────────────────────────────────┘
```

## Usage

```bash
terraform init
terraform apply -var project_id=my-project \
  -var image=us-docker.pkg.dev/my-project/sagaz/outbox-worker:1.8.3
# or: terraform apply -var-file=examples/minimal.tfvars
terraform destroy   # what `sagaz deploy teardown` runs
```

Build and push the image from the repository `Dockerfile` first. The module sets
the container command explicitly (`var.worker_command`, default
`python -m sagaz.core.outbox.worker`), so it does not depend on the image `CMD`.
The image must contain the `redis` extra.

## Why a worker pool and not a Cloud Run service

The outbox worker is a long-running consumer that never listens on a port (it
does not start the Prometheus HTTP server). A Cloud Run **service** must listen on
`$PORT`: its default TCP startup probe would fail and the revision would never
become ready, even with `min_instance_count >= 1` and `cpu_idle = false`.

Cloud Run **worker pools** (`google_cloud_run_v2_worker_pool`, GA since April 2026
and available in the `hashicorp/google` provider (6.x and later) without `google-beta`) are made
for pull-based background work: no endpoint, no port requirement, no startup
probe on `$PORT`, always-allocated CPU, and a fixed instance count
(`scaling_mode = "MANUAL"`, `manual_instance_count = var.worker_count`). Health is
the process itself: if the worker exits, Cloud Run restarts the instance.

To run on a Cloud Run service instead, the worker would need an HTTP listener on
`$PORT` (for example `start_http_server` from `sagaz.observability.monitoring`
on `$PORT`) so the startup probe passes.

## Networking

- With `network = null` (default) the module creates a VPC and a subnet
  (`subnet_cidr`, default `10.10.0.0/24`). With an existing network, set both
  `network` and `subnetwork`; if that network already has a servicenetworking
  peering, set `create_private_service_access = false`.
- Cloud SQL (`ipv4_enabled = false`, `ssl_mode = ENCRYPTED_ONLY`) and Memorystore
  (`connect_mode = PRIVATE_SERVICE_ACCESS`) get private IPs from a range reserved
  for **Private Service Access**.
- The worker reaches them through **Direct VPC egress** (GA, no connector VMs to
  pay for or size) with `egress = PRIVATE_RANGES_ONLY`; public traffic (Google
  APIs, the image registry) does not go through the VPC, so no Cloud NAT is needed.
  The Serverless VPC Access connector is not used.

## Secrets and identity

- The database password comes from `random_password` (alphanumeric, 32 chars); the
  Memorystore AUTH string is generated by Google. Both are only written into two
  Secret Manager secrets, `<name>-<environment>-database-url` and
  `<name>-<environment>-redis-url`, holding the complete URLs.
- They are mounted as environment variables `DATABASE_URL` and `REDIS_URL` on the
  worker, pinned to the secret version Terraform created (a change rolls out a new
  revision).
- The worker runs as a dedicated service account with only
  `roles/secretmanager.secretAccessor` on those two secrets and
  `roles/cloudsql.client` on the project.
- Values also end up in the Terraform state (as for every Terraform-managed
  secret): use a remote backend with restricted access (for example a GCS bucket).

Worker environment: `BROKER_TYPE=redis`, `REDIS_SSL`, `SAGAZ_OUTBOX_MODE`, the two
secrets, and anything in `worker_env` (e.g. `BATCH_SIZE`, `POLL_INTERVAL`,
`MAX_RETRIES`, `WORKER_ID`, `LOG_LEVEL`). `worker_env` cannot override
`DATABASE_URL` or `REDIS_URL`.

`DATABASE_URL` is `postgresql://sagaz:…@<private-ip>:5432/sagaz?sslmode=require`
(encrypted, the server certificate is not verified).

### Redis in-transit encryption

`redis_transit_encryption = false` by default. With `true`, Memorystore uses
`SERVER_AUTHENTICATION` TLS on port 6378 and the worker gets
`rediss://:AUTH@host:6378/0?ssl_cert_reqs=none`: traffic is encrypted, but the
server certificate is not verified, because Memorystore's per-instance CA is not
in the image trust store. To verify it, bake the CA from
`google_redis_instance.server_ca_certs` into the image and drop
`ssl_cert_reqs=none` (override `worker_env` / the secret accordingly).

## CDC mode (`outbox_mode = "cdc"`)

Sets `SAGAZ_OUTBOX_MODE=cdc` and `SAGAZ_CDC_SOURCE=pg_logical` on the worker and the
Cloud SQL flag `cloudsql.logical_decoding = on` (changing it **restarts** the
instance). The worker also needs a role with `REPLICATION` to create its slot; Cloud
SQL users created through the API do not have it, and Terraform cannot run SQL on a
private-only instance. Run the statement from the `cdc_setup_sql` output once, as a
`cloudsqlsuperuser` (for example in Cloud SQL Studio):

```sql
ALTER USER "sagaz" WITH REPLICATION;
```

A replication slot retains WAL while the worker is stopped; storage auto-resize is
on, so monitor `pg_replication_slots` (see `docs/integrations/cdc.md`).

## Teardown and deletion protection

> **Warning:** `deletion_protection` defaults to `false` so that
> `terraform destroy` / `sagaz deploy teardown` works. Destroying deletes the Cloud
> SQL instance **and its automated backups**. Set `deletion_protection = true` for
> production data; teardown then fails until you set it back to `false` and apply.

The Private Service Access peering uses `deletion_policy = "ABANDON"` (Google keeps
it busy for a while after Cloud SQL is deleted); it is removed with the VPC. A
destroyed Cloud SQL instance name cannot be reused for about a week, so the name
carries a random suffix. Enabled APIs are left enabled.

## Outputs

`database_endpoint` (private IP), `database_connection_name`, `redis_endpoint`
(`host:port`), `worker_service_name` (worker pool), `worker_service_account`,
`database_url` and `redis_url` (sensitive), `secret_ids`, `log_filter`, `log_url`,
`network`, `cdc_setup_sql`.

Logs: `gcloud logging read "$(terraform output -raw log_filter)" --limit 50`.

## Cost

`cost.json` holds approximate us-central1 list prices used by
`sagaz deploy --provider gcp --cost-estimate`. The defaults (1 worker with 1 vCPU and
512 MiB, db-f1-micro with 10 GB, 1 GB BASIC Memorystore) come to roughly
$7.67 + $1.70 + $47.30 + $2.63 + $35.77 + $0.12 ≈ **$95/month** before the Cloud Run
free tier and discounts. The worker pool lines use instance-based Cloud Run rates
and are an upper bound.
